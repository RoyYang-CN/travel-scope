核心工作流 (8步)

1

交互收集参数

通过问答收集以下参数（合并为尽量少的轮次，已提供的跳过）：

标准化 Q0-Q3

Q0 目的地范围、Q1 出行月份/日期、Q2 旅行天数、Q3 预算档位。

标准化 Q4-Q9

Q4 出行方式（仅自驾/非自驾）；Q5 抵达口岸；Q6 离开口岸；Q7 搜索深度；Q8 地图平台；Q9 路线方案。国内非自驾时，另触发公共交通或包车/接送的交通规划分支。

自动判断：国内以高德 POI 为主、百度重点核验/补图/导航，搜索引擎作辅助；海外按可用地图与公开来源执行。平台缺失字段不伪造，AI 推荐分单独标注。
2

数据源判断与目的地盘点

在线搜索补充8-16个主要旅行目的地的信息：

  • 名称（中英文）、所属区域、核心体验
  • 建议天数、最佳季节、到达方式
3

路线设计

根据地理位置和交通可行性，设计3-6条备选路线方案（ROUTES数组）：

  • 每条包含：方案名、天数、路线串联、特色、适合人群、预算、交通方式
3.5

每日行程编排 (ITINERARY) 全量编排

所有路线方案都必须编排完整每日行程，确保HTML下拉每条方案都有完整的地图路线展示。

全量编排原则：不要只编排1-2条主路线！否则用户切换方案时看到空白页面，体验极差。多方案通常有大量重叠点位，先编排方案A，再基于A的骨架调整出其他方案。
字段说明
方案名对应ROUTES中的方案名称
日序"Day 1", "Day 2", ...
序号当日顺序（1,2,3...）
点位类型景点 / 餐厅 / 酒店 / 交通
点位名称必须与HOTELS/RESTAURANTS/ATTRACTIONS的[1]中文名完全一致
经纬度WGS84格式 "纬度,经度"
编排经验：每天4-6个点位；跨城市移动用交通类型标注；新增城市需先.extend()追加数据再编排
4

深度数据收集（含交叉验证）

对每个目的地按数据源分流规则收集数据，每个点位交叉验证至少N篇：

国内评分格式

酒店/景点：小红书热度:高|携程:4.5
餐厅：大众点评:4.5分|850条

海外评分格式

统一：Google:4.3 或 Google:4.3|1200条

交叉验证流程

搜索点位名→多源提取N篇→核对名称/地址/评分→剔除已关闭→独立确认坐标

11字段格式：HOTELS [目的地,中文名,英文名,类型,参考价,评分,评价数,经纬度,图片1,图片2,特色描述]
5

交通 + 实用信息

收集目的地间交通方式（航班/快船/大巴/自驾/火车）和签证/汇率/SIM卡等实用信息

6

坐标获取 高德POI API

国内目的地坐标必须通过高德POI搜索获取（WGS84格式存储）：

GET https://restapi.amap.com/v3/place/text
    ?key=YOUR_AMAP_KEY
    &keywords=点位名
    &city=城市名
    &extensions=all  # 返回坐标+图片
坐标转换：高德API返回GCJ02坐标（火星坐标系），存储到数据数组前必须转换为WGS84！
API返回 location 格式是 "经度,纬度"（经度在前），存储需反转为 "纬度,经度"
7

图片搜索与补全 高德photos优先

按优先级获取图片：

优先级方式命中率
1高德POI API photos字段（extensions=all返回）~81%
2在线搜索（携程/马蜂窝/大众点评图片）~15%
3留空显示📷占位图—
实战经验：高德POI API一步获取坐标+图片，效率最高。64个缺图点位测试：52个找到图片(81%)，无防盗链限制，图片可正常加载。找不到的主要是小型经济宾馆和偏远景点。
批量补全模式：先运行脚本生成初版三件套→用高德POI API批量查询缺图点位→注入图片URL→重新生成

扩展城市数据模式

当追加新城市POI数据时（如方案B/C涉及新城市），使用.extend()追加：

# 在合并脚本中追加新城市数据
HOTELS.extend([
    ["满洲里", "满洲里大饭店", "Manzhouli Grand Hotel", ...],
])
RESTAURANTS.extend([...])
ATTRACTIONS.extend([...])
先追加数据再编排行程：新城市的点位数据必须先.extend()到数组中，才能在ITINERARY中引用这些点位名称
