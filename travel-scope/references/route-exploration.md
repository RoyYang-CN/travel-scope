# 路线走廊探索规范

路线探索与景点/酒店搜索是两个独立阶段。国家级输入、跨区域输入和群岛型目的地必须先建立“目的地节点—交通边—主题走廊”图，再进入点位深搜。

## 深度规则

- POI 深度：搜索景点、餐厅、住宿及价格、图片、评价证据。
- 路线深度：发现城市、景区、港口、机场之间的成熟旅行走廊，并验证顺路性、交通方式、季节风险和进出方式。
- 用户没有指定具体区域时，路线深度自动至少为 deep；国家较大、群岛多或存在陆路/渡轮组合时，自动升级为 super route exploration。
- “入境/离境城市”只提供交通约束，不等于旅行范围；机场城市必须向陆路和海路两侧扩展。

## 必须形成的记录

每条走廊至少记录：`corridor_id`、名称、节点顺序、节点主题、入口/出口、交通边、预计用时、绕行风险、季节风险、证据链接和纳入状态。每个候选目的地必须满足以下之一：

1. 纳入一条或多条候选走廊；
2. 明确排除，并写明天数、交通、季节、口岸、绕行或数据不足原因；
3. 标记为待验证，不得静默消失。

## 强制反漏检

## 经典走廊反漏检（v2.7.3）

国家级输入或大型区域输入必须在路线探索输入中增加 `classic_corridors`。它不是固定国家名单，而是针对当前目的地从官方旅游局、交通运营方、成熟旅行社路线和多篇独立攻略中发现的成熟多日组合。至少检查网关城市连接的自然/文化腹地、火山/国家公园/海岸/海岛连续线路、港口或渡轮连接的岛链，以及官方资料反复出现的多日路线。

每条经典走廊必须记录 `corridor_id`、名称、节点顺序、主题、典型天数、证据链接和状态。状态只能是 `candidate`、`covered`、`excluded` 或 `pending`；排除必须填写 `exclude_reason`。`route_explorer.py` 会检查全部节点是否被同一条候选走廊完整覆盖，未覆盖且未明确排除的走廊会阻断后续 POI 深搜。

最小格式：

```json
{
  "classic_corridors": [
    {
      "corridor_id": "classic_example",
      "name": "网关城市—自然腹地—海岛",
      "nodes": ["网关城市", "自然腹地", "海岛"],
      "themes": ["自然", "海岛"],
      "typical_days": 6,
      "evidence_urls": ["https://example.com/source"],
      "status": "candidate"
    }
  ]
}
```

这一步解决“城市被搜到，但成熟路线没有被识别”的问题；它与后续路线独立性 QA 不同，前者防止规划前漏掉经典走廊，后者防止生成后路线内容重复或空洞。

不能只按机场、城市热度或单点搜索结果生成路线。必须检查：

- 主要网关城市是否连接到相邻的火山、海岛、国家公园和港口；
- 陆路、渡轮、短途航班是否构成连续链路；
- 是否存在成熟的多日旅行走廊；
- 推荐路线是否造成明显回头路；
- 走廊中的著名节点是否被误当成“非城市”而漏掉。

## 区域内部拆解（v2.7.2）

国家级目的地发现完成后，对进入路线的“大岛、大区或超级目的地”必须再执行一次内部拆解，不能把整座岛只记录为一个节点。至少拆成：核心城市/文化区、自然或火山区、东/南/西/北海岸、近海岛屿、港口/机场和成熟的一日或多日子线路。

对于存在强经典线路的目的地，必须建立 `subcorridor` 记录，并至少包含：`parent_destination`、`nodes`、`edges`、`themes`、`typical_days`、`season_risk`、`evidence_urls`。例如巴厘岛至少主动检查：

- 中部文化线：乌布—德格拉朗—圣泉寺；
- 东/东南海岸线：沙努尔—帕当拜—艾湄湾/图兰奔；
- 佩尼达海岛线：沙努尔—蓝梦岛—佩尼达岛；
- 西北生态线：佩母德兰—门姜岸—西巴厘岛国家公园；
- 北部慢旅行线：罗威那—北巴厘岛温泉/瀑布。

一个“大岛”节点只有在完成内部拆解后，才允许作为路线方案的单一目的地使用。

## 路线独立性门禁

AI自动推荐的多条路线必须是不同的旅行逻辑，不得只改路线名称。每条路线都要有自己的：

- 入口/出口和节点顺序；
- 主题组合；
- 经典节点清单；
- 每日区域分配；
- 交通和天气风险。

如果某条路线缺少点位数据，不得复用另一个区域的点位填充；应暂停该路线、补搜数据或把它降级为“待验证”。

## route_plan.json 最小格式

进入 POI 深搜和每日编排前，运行目录必须保存每条方案的语义计划。`required_poi_names` 是路线必须在 ITINERARY 中出现的经典节点，不是可选推荐；若数据不足，应把路线标记为待验证，不得删除字段后继续生成。

```json
{
  "routes": [
    {
      "name": "方案A（火山—伊真—西巴厘岛）",
      "nodes": ["泗水", "布罗莫", "外南梦/伊真", "佩母德兰", "巴厘岛南部"],
      "themes": ["火山", "生态", "海岛"],
      "required_poi_names": ["布罗莫火山", "伊真火山", "门姜岸"],
      "daily_areas": ["泗水", "布罗莫", "外南梦", "西巴厘岛", "巴厘岛南部"],
      "status": "candidate"
    }
  ]
}
```

`validate_output.py --route-plan-json` 会检查计划中的路线是否存在，以及经典节点是否实际进入该路线的 ITINERARY；同时检查点位数量、每日结构和路线间重合度。这个文件不能由生成器在路线编排完成后临时补写，必须作为路线设计阶段的输入和审计证据。

## 印度尼西亚前向测试基准

应主动识别并比较：`泗水 → 布罗莫 → 外南梦/伊真 → Ketapang–Gilimanuk → 西巴厘岛/佩母德兰/门姜岸 → 北巴厘岛/罗威那 → 巴厘岛南部`。这条链路不是把泗水、外南梦、巴厘岛分别列为城市，而是把它们识别为连续的火山—生态—海岛走廊；二月方案还必须保留火山开放、道路、降雨和渡轮状态的动态核验。
