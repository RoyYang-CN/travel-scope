# Travel-Scope

## v3.1.0 图片真实性与跨城市输出闭环门禁（强制）

- Live 输出严禁使用算法合成、虚构或无法实际访问的图片 URL；旧城市 payload 不能因格式正确而直接复用。
- 海外 Live 图片必须来自 Google Places API (New) 的具体 POI 图片映射；旧的 Unsplash 模板字段必须重新采集。
- 生成前先执行 `scripts/gen_travel_scope.py` 的来源/唯一性检查；生成后必须执行 `scripts/validate_output.py --verify-remote-images`，逐张确认 HTTP 200 且内容类型为 `image/*`。
- 任一图片返回 404、非图片内容、虚构 ID、跨 POI 复用或类别错配时，阻断正式交付；不得用其他类别图片或查询参数伪装通过。
- 所有城市构建脚本必须把统一采集器输出回写到 payload，再调用公共生成器；不能在城市脚本中定义静态图片常量。

## v3.0.3 分类自适应与图片类别门禁（强制）

- `DIVE_SITES` 只允许真实潜水、浮潜、水肺或明确潜点记录；帆船、皮划艇、观鲸、游船、摩托艇等水上活动必须归入普通景点/活动，不得显示为“潜水”。
- 当目的地没有真实潜水记录时，HTML、Markdown、Excel 不得生成潜水分类或潜水统计；路线中的同类水上活动同步按景点/活动处理。
- 图片必须按住宿、餐厅、景点和水上活动类别获取或注入；全品类混用的随机模板图不能作为 Live 正式点位图片。
- 生成后必须检查图片来源类别与 POI 类别一致；无法确认图片属于当前 POI 或类别时，保留缺图状态并阻断正式交付，不得用其他类别图片冒充。

- 国际 Live 数据必须为每个酒店、餐厅、景点提供已验证的 Google Place ID 和两张 POI 级 Google 图片；没有实体 ID 时不得依赖坐标生成看似正确的导航链接。
- Google Maps 链接统一采用 Place ID/名称优先、坐标备用；HTML 卡片、路线面板和 Excel 坐标汇总必须调用同一规则。
- 国际 Excel 必须包含 Google 图片1、Google 图片2、Google Place ID，并与 HTML 使用同一份 POI 数据。
- 国内不改变高德主接口、百度验证/补图/导航的既定逻辑；正式 Live POI 必须保留高德 POI ID，用于审计名称与 WGS84 坐标一致性。
- 国内/国际均阻断跨 POI 图片 URL 复用；Demo 夹具不代表真实数据质量。

## v2.6 交付门禁（强制）

使用 `scripts/gen_travel_scope.py` 生成交付物时，默认执行严格数据校验；不要用 `--no-strict-qa` 生成正式交付。严格校验会在生成前阻断以下问题：

- 酒店、餐厅、景点缺少价格参考值或仍使用“待核验/待补充”等占位值；
- 点位缺少两张可访问的 HTTP(S) 图片 URL；
- ITINERARY 点位不在 POI 数据中；
- ROUTES 中的方案没有对应的完整每日行程，或缺少指定旅行天数；
- 行程坐标格式错误。

生成后必须运行独立门禁：

```powershell
python scripts/validate_output.py `
  --html <输出目录>/<国家>旅行攻略-地图标记.html `
  --delivery-xlsx <输出目录>/<国家>旅行攻略大全.xlsx `
  --research-xlsx <输出目录>/<国家>旅行攻略研究版.xlsx `
  --scope-json <运行目录>/destination_scope.json `
  --route-plan-json <运行目录>/route_plan.json `
  --expected-days <旅行天数>
```

只有输出 `PASS` 才能交付。该门禁检查目的地覆盖、每个卡片两张图片、价格占位、Excel 工作表数量、所有路线方案、每日行程天数、每天至少两个行程点及路线点位双图。随后仍需启动本地 HTTP 服务进行浏览器实测，验证图片实际加载、Tab 切换和每条路线切换；不能只依赖静态字符串检查。

## v2.7 路线走廊门禁（强制）

v2.7 新增独立的路线探索阶段，不能用 POI 搜索代替。国家级、跨区域和群岛型目的地默认执行 deep route exploration；存在陆路、渡轮或火山—海岛组合时自动升级为 super route exploration。执行 `scripts/route_explorer.py`，并将输出保存为运行目录中的 `route_corridors.json`。

路线探索必须在酒店、餐厅、景点深搜之前完成。机场/口岸只约束起终点，必须向相邻陆路景区、港口、国家公园和海岛扩展。每个候选目的地必须进入走廊、明确排除并写原因，或标记待验证，不能静默消失。正式路线还必须通过交通边审计，不能出现没有记录连接的相邻节点。规范见 `references/route-exploration.md`。

## v2.7.2 路线质量门禁（强制）

在国家级走廊之后，必须对已纳入的大岛/大区执行内部拆解，形成 `subcorridors`。巴厘岛至少检查中部文化、东/东南海岸、蓝梦岛—佩尼达岛、西北生态和北部罗威那等子线路。多路线输出还必须通过 `validate_output.py` 的路线独立性门禁：每条路线要有足够的独特点位和每日结构，不得用同一组两个点重复14天；路线名称、经典节点和实际 ITINERARY 必须一致。发现数据不足时必须暂停该路线或标记待验证，禁止复用其他区域点位填充。

## v2.7.3 经典走廊反漏检门禁（强制）

国家级或大型区域攻略必须在 `route_exploration_input.json` 中建立 `classic_corridors`，由官方旅游资料、交通运营方和独立路线证据发现成熟多日组合。`route_explorer.py` 会检查每条经典走廊是否被某条候选路线完整覆盖；未覆盖的走廊必须明确排除并写原因，或标记待验证后暂停深搜，不能静默忽略。该规则不绑定印度尼西亚，适用于所有国家、地区、岛屿群和大型国内区域。

## 概述

为用户制作覆盖多个目的地的完整旅行攻略，输出交付三件套和独立研究工作簿：
1. **交付版 Excel**（基础10个工作表；存在真实潜水时增加“潜水活动”工作表）
2. **研究版 Excel**（14个工作表：交付版11个工作表 + 目的地覆盖、来源证据、动态信息）
3. **Markdown**（完整文字攻略，可直接阅读，含每日行程详情章节）
4. **HTML地图标记页**（双视图Tab切换：①卡片列表视图——按目的地城市分类→住宿/美食/景点/潜水/交通子分类→具体地点，每个点位含2张图片展示+lightbox大图，可点击一键导航；②地图路线视图——使用高德JS API嵌入真实地图，按每日行程顺序用连线串联景点/餐厅/酒店点位，Marker按类型着色，InfoWindow含图片+导航按钮，左侧行程面板可点击定位）

### v2.9 国际化输出门禁（强制）

Travel-Scope 使用同一份已通过 QA 的结构化数据生成不同语言输出，不得为英文版另行编排一套路线或重新臆造点位。

- `--language cn`：生成现有中文交付物，保持默认文件名。
- `--language en`：生成英文 HTML、Markdown 和 Excel，文件名增加 `-en` 后缀。
- `--language both`：连续生成 CN 和 EN 两套交付物；两套必须来自同一份目的地、POI、交通、路线和证据数据。
- 英文版优先展示英文名称，同时保留中文名称，格式为 `English Name (中文名)`，便于国际游客问路、打车和现场核对。
- 目的地区域标题和路线方案名称也属于动态名称，必须提供 `name_en`/英文方案名；生成器不得只翻译固定 UI 后继续输出中文标题。
- 中文名、英文名、拼音、中文地址、英文地址、坐标、地图链接和来源状态属于结构化字段；缺失英文名时不得编造，保留中文并标注待补充。
- 英文生成前必须执行动态语言门禁；目的地或路线英文名缺失时阻断正式 EN 交付并指出缺失字段，不能让不完整英文结果进入 README、案例或发布包。
- 英文版必须保留 Google Maps 导航；中国目的地同时提供高德和百度静态导航链接，不因输出语言改变地图坐标或路线逻辑。
- 中国国际游客信息应写入统一的 `PRACTICAL`/`DYNAMIC_INFO` 数据：签证、支付、网络、铁路/机场交通、预约、实名制、中文点名、英语服务和外卡支付等；不得散落在生成器硬编码文本中。
- AI 推荐分必须在两种语言中明确标注为 AI 提供、仅供参考、非平台评分；平台评分、搜索补充和 AI 分不能合并。
- 英文输出不是“把中文页面字符串机械替换”为英文：稳定 UI 和表头必须英文；来源描述、动态政策和用户输入文本缺少可信翻译时保留原文并标注语言状态。

详细字段和中国国际游客信息规范见 [references/internationalization.md](references/internationalization.md)。

### v2.9.1 开源 Demo / Live 门禁（强制）

- `--mode demo` 只读取 `fixtures/demo.json` 或 `--fixture <脱敏JSON>`，不调用高德、百度、Google 或搜索引擎 API，不需要任何 API Key。
- Demo 输出必须明确标注 `Demo fixture`、`offline sample data` 或等价提示，不得作为真实旅行建议或实时平台评分。
- `--mode live` 为真实数据模式，继续执行正式来源审计、路线门禁和全链路 QA；API Key 只能来自环境变量或运行时安全注入，不能写入仓库。
- Demo 模式允许展示占位图和示例导航链接；Live 正式交付仍遵守图片、评分、坐标、来源和路线完整性门禁。
- 开源 README 必须同时说明 Demo 与 Live 的差异，并给出不需要 Key 的最短运行命令。

## 交互式信息收集（标准化 Intake SOP）

启动后，通过 `question` 工具向用户收集以下参数。**分两轮批量弹出，已由用户在初始消息中提供的参数自动跳过。**

### 标准化 Q 门禁（强制）

所有旅行攻略必须使用同一组字段、同一顺序和同一跳过规则，不得根据代理临时习惯增删问题或改变顺序。用户一次性提供部分参数时，只询问缺失字段；已提供字段必须回显为“已确认”，不得重复询问。

固定顺序如下：

**Q0 范围**：国家/地区、城市、景区、区域、线路或多个自定义目的地。

**Q1 时间**：出行月份或具体日期。

**Q2 天数**：旅行天数。

**Q3 预算**：经济 / 中档舒适 / 高端豪华 / 混合 / 自定义。

**Q4 出行方式**：仅两项——自驾 / 非自驾。

**Q5 抵达口岸**：海外为入境机场、城市或港口；国内为抵达城市或交通节点。

**Q6 离开口岸**：海外为离境机场、城市或交通节点；国内为离开城市或交通节点。

**Q7 搜索深度**：浅 / 中 / 深 / 超级深 / 自定义。

**Q8 地图平台**：Google Maps / 高德地图 / 百度地图 / 全部。默认海外 Google Maps、国内高德地图。

**Q9 路线方案**：3条 / 5条 / 7条 / 自定义 / AI自动推荐。默认 AI自动推荐。

> **Q4 分支规则**：国内选择“自驾”时，重点规划道路、驾驶距离、路况、停车和车辆要求；不强制搜索公共交通。国内选择“非自驾”时，必须搜索城际交通、班次、费用和耗时，并将交通节点纳入每日行程。国际目的地即使选择“自驾”，仍必须识别无法自驾完成的渡轮、岛间船和接驳。
>
> **Q4 缺失兜底**：用户未提供 Q4 时，自动按“非自驾”处理，并在参数确认单中明确标注“Q4 未提供，已按非自驾兜底”；不得因此暂停流程。

提问规则：

1. 缺少 Q1-Q6 时，先按 Q1→Q6 顺序提问；缺少 Q7-Q9 时，再按 Q7→Q9 顺序提问。
2. Q0 已由用户明确提供时不重复问；若只提供国家，则记录为国家级输入并继续询问 Q1-Q9。
3. 用户回答“默认”或“都用默认”时，只对未提供字段应用默认值；海外/国内口岸仍然必须明确，不能默认首都或机场。
4. 收齐后必须输出一段固定格式的“参数确认单”，列出 Q0-Q9 的最终值；用户确认或没有提出修改后，才进入目的地发现。
5. 不得在参数收集阶段临时增加“旅行风格”等非标准问题；偏好通过路线方案和推荐理由体现。

### Q确认后的自动连续执行（强制）

用户确认 Q0-Q9 后，代理必须自动连续执行目的地发现、经典走廊审计、区域内部拆解、POI 深搜、路线编排、生成和 QA。阶段性进度汇报只能作为非阻塞更新，不能以“请确认下一步”或等待用户再次输入作为阶段切换条件。只有以下情况允许暂停并向用户提问：Q0-Q9 仍有真实缺失、用户要求改变范围/预算/天数，或外部数据冲突会实质改变路线方向且无法通过证据解决。普通候选排除、路线排序、搜索关键词调整、API 重试和质量修复均由代理自动处理。

**当前缺失字段的标准提问模板**：

> 已确认：Q0 目的地范围、Q2 旅行天数。
> 
> 请补充以下参数：
> Q1 出行月份/日期：
> Q3 预算：经济 / 中档舒适 / 高端豪华 / 混合 / 自定义
> Q4 出行方式：自驾 / 非自驾
> Q5 抵达口岸：
> Q6 离开口岸：
> Q7 搜索深度：浅 / 中 / 深 / 超级深 / 自定义
> Q8 地图平台：Google Maps / 高德地图 / 百度地图 / 全部
> Q9 路线方案：3条 / 5条 / 7条 / 自定义 / AI自动推荐

> **口岸规则 [CRITICAL]**
> - **海外目的地**：必须询问入境口岸和离境口岸，**严禁自动默认首都**。如用户说“菲律宾”，需问“从哪个城市/机场入境？（如马尼拉、宿务、卡利博）”和“从哪个城市/机场离境？”。用户可能从宿务入境、马尼拉离境（开口程），路线起点和终点完全不同。
> - **国内目的地**：必须询问抵达城市和离开城市。如用户说“大兴安岭”，需问“从哪个城市抵达？（如海拉尔、加格达奇）”和“从哪个城市离开？”。
> - 口岸已由用户在初始消息中说明的，跳过不问。
> - 国内/海外判断：根据目的地自动判断，中国大陆→国内规则，其他→海外规则。

## 交叉验证机制

每个点位（酒店/餐厅/景点）的数据必须经过**交叉验证**——即从多个独立来源确认该点位真实存在且信息准确。

### 验证篇数参数

验证篇数由用户选择的**搜索深度**自动决定，不再作为独立参数询问：
- 浅：交叉验证5篇
- 中：交叉验证10篇
- 深：交叉验证15篇
- 超级深：交叉验证23篇（深度15篇的1.5倍向上取整）
- 自定义：用户在自定义搜索深度时一并指定

交叉验证的“篇数”指独立来源或独立页面，不是同一平台的重复转载。对于官方营业状态、票价、开放时间等事实，应优先保留官方来源，即使不计入普通攻略文章数量。

每个点位至少需要交叉验证N篇内容（攻略/点评/新闻/官方介绍等）。

### 交叉验证实操流程

对每个点位执行以下步骤：

1. **搜索点位名称**：搜索 `"点位名 + 目的地"` 关键词
2. **多源提取**：从搜索结果中提取至少N篇不同来源的内容
   - 国内搜索策略：优先搜索 `小红书 "点位名" 目的地`、`大众点评 "点位名"`、`携程 "点位名" 评分`
   - 海外搜索策略：优先搜索 `"point name" destination review`、`TripAdvisor "point name"`、`Google Maps "point name"`
3. **交叉核对**：
   - 名称是否一致（排除同名不同店的情况）
   - 地址/位置是否吻合
   - 评分/价格是否在合理范围
4. **剔除验证**：如果N篇中有超过2篇提及该点位不存在或已关闭，则剔除该点位换替代项
5. **坐标独立确认**：坐标必须从高德POI（国内）或Google Maps（海外）单独确认，**不从攻略中推断**

### 搜索效率优化

- 同一轮最多发起2个并行搜索请求
- 按城市批次搜索，避免频繁切换上下文
- 大型知名景点/酒店通常1-2轮搜索即可确认；小型餐厅/民宿可能需要3-4轮
- 如果搜索结果不足N篇，应换用不同关键词组合重试（如去掉地名、换用英文名等）

## 坐标获取实操指南

### 国内目的地（高德POI搜索）

对每个点位，通过高德地图POI搜索获取其精确坐标。有两种实操方式：

#### 方式A：在线搜索获取坐标

1. 搜索 `"点位名" 高德地图` 或 `"点位名" 经纬度 目的地`
2. 从搜索结果中提取经纬度信息
3. 坐标格式统一为 `"纬度,经度"`（如 `"49.1856,119.6503"`）
4. 如果搜索不到精确坐标，搜索该点位所在的街道/地标，使用该地标坐标
5. **严禁**使用城镇中心坐标替代具体点位坐标——除非确实无法获取

#### 方式B：高德POI搜索API直接获取（推荐）

调用高德Web服务API直接获取POI坐标，精度最高：

1. **调用API**：
   ```text
   https://restapi.amap.com/v3/place/text?key=YOUR_AMAP_KEY&keywords=点位名&city=城市名&offset=5&page=1&extensions=all
   ```
2. **提取坐标**：返回JSON中 `pois[0].location` 为 GCJ02 坐标，格式 `"经度,纬度"`
3. **转换为 WGS84 存储**：高德API返回的是 **GCJ02（火星坐标系）**，数据数组中必须存储 **WGS84** 格式，必须做 GCJ02→WGS84 转换
4. **转换代码**（Python 迭代法，30次迭代精度足够）：
   ```python
   import math
   def gcj02_to_wgs84(lat, lng, iterations=30):
       wgs_lat, wgs_lng = lat, lng
       for _ in range(iterations):
           dlat = transform_lat(wgs_lng - 105.0, wgs_lat - 35.0)
           dlng = transform_lng(wgs_lng - 105.0, wgs_lat - 35.0)
           radlat = wgs_lat / 180.0 * math.pi
           magic = math.sin(radlat)
           magic = 1 - 0.00669342 * magic * magic
           sqrtmagic = math.sqrt(magic)
           dlat = (dlat * 180.0) / ((6378245.0 * (1 - 0.00669342)) / (magic * sqrtmagic) * math.pi)
           dlng = (dlng * 180.0) / (6378245.0 / sqrtmagic * math.cos(radlat) * math.pi)
           gcj_lat = wgs_lat + dlat
           gcj_lng = wgs_lng + dlng
           wgs_lat = lat - (gcj_lat - wgs_lat)
           wgs_lng = lng - (gcj_lng - wgs_lng)
       return wgs_lat, wgs_lng
   # 用法：gcj02_to_wgs84(lat, lng) → (wgs84_lat, wgs84_lng)
   ```
5. **存储格式**：转换后存储为 `"纬度,经度"` 字符串（纬度在前，经度在后）

> **重要提醒**：高德POI API返回的 `location` 字段格式是 `"经度,纬度"`（经度在前），存储到数据数组时需要反转为 `"纬度,经度"`（纬度在前），同时做 GCJ02→WGS84 转换。

> **坐标存储格式**：所有坐标以 WGS84 格式存储在数据数组中。脚本内的 `wgs84_to_gcj02()` 和 `wgs84_to_bd09()` 函数会自动转换为各地图平台所需坐标系。海外目的地（经纬度超出中国大陆范围）脚本自动跳过转换，使用原始坐标。

### 海外目的地（Google Maps）

1. 搜索 `"point name" destination google maps`
2. 从搜索结果中提取经纬度
3. 格式同上：`"纬度,经度"`

## 图片搜索与填充流程

### 图片搜索策略（按目的地类型分流）

#### 海外目的地：Google Places API (New) 批量搜图

使用 Google Places API (New) 的 Text Search + Nearby Search 双策略批量获取图片，效率最高（菲律宾 404 个 POI，8 线程并行，37 秒完成，命中率 97%）。

**前置条件检查 [CRITICAL]**

搜图前必须完成以下检查，否则会浪费时间排查超时：

1. **代理状态验证**：Clash Verge 必须处于"已开启"状态（不仅 service 进程在跑，代理核心也要启动）
   - 检查 `verge_mixed_port` 是否监听：读取 `C:\Users\<用户>\AppData\Roaming\io.github.clash-verge-rev.clash-verge-rev\verge.yaml` 中的 `verge_mixed_port`（默认 7897）
   - 用 `Test-NetConnection -ComputerName 127.0.0.1 -Port <端口>` 验证端口可连接
   - 如果端口不通，告知用户启动 Clash Verge 并等待，不要盲目重试
2. **API 连通性测试**：用 3 个 POI 做快速测试（timeout=10s），5 秒内有返回才算通过
3. **代理环境变量**：Python 运行时必须设置 `$env:HTTP_PROXY="http://127.0.0.1:<端口>"; $env:HTTPS_PROXY="http://127.0.0.1:<端口>"`

> **[CRITICAL] 代理排查教训**：菲律宾攻略搜图时，Clash Verge service 进程在运行但代理核心未启动，混合端口 7897 无人监听。直接运行搜图脚本导致全部超时（10分钟只处理2个POI）。排查代理配置花费大量时间。必须在搜图前做前置检查。

**搜图脚本模板**（参数化，复用时只需改 3 个变量）

变量：`API_KEY`、`INPUT_JSON`（merged POI JSON 路径）、`OUTPUT_FILE`（输出 JSON 路径）

核心逻辑：
1. 从 merged JSON 读取全部 POI（中文名、英文名、经纬度、分类）
2. 对每个 POI 执行三级搜索策略：
   - Strategy 1: Text Search (`places:searchText`) — 最精确，按英文名 + 5km 半径 locationBias 搜索
   - Strategy 2: Nearby Search (`places:searchNearby`) — 1km 半径 fallback
   - Strategy 3: Nearby Search 3km 半径 — 更广范围 fallback
3. 取首个匹配结果的 `photos` 字段（最多2张），构建图片 URL：`https://places.googleapis.com/v1/{photo_name}/media?maxWidthPx=400&key={API_KEY}`
4. 8 线程并行（`ThreadPoolExecutor(max_workers=8)`），每批 40 个 POI，每批结束后 checkpoint 保存
5. 支持断点续搜（读取已有 `photos.json`，跳过已搜过的 POI）
6. 输出格式：`{"中文名": ["url1", "url2"], ...}`

**Google Places API (New) 要点**：
- classic Places API 已被标记 deprecated，返回 `REQUEST_DENIED`，必须用新版
- 请求头需设置 `X-Goog-Api-Key` 和 `X-Goog-FieldMask`（指定返回字段，如 `places.id,places.displayName,places.photos`）
- Text Search 用 `locationBias`（circle + center + radius），Nearby Search 用 `locationRestriction`
- `pageSize` 建议设为 3（取前3个结果中的第一个的 photos）

#### 国内目的地：高德 POI API 搜图

1. 调用 `https://restapi.amap.com/v3/place/text?key=KEY&keywords=点位名&city=城市名&extensions=all`
2. 返回的 `pois[0].photos` 包含真实图片 URL（高德用户上传+官方图）
3. 一个 API 调用即可获取坐标+图片，效率最高（实测 64 个缺图点位 52 个找到图片，81% 命中率）
4. 按 `online_search` 工具搜索图片为备选方案（设置 `resource_type_filter=[{"top_k":5,"type":"image"}]`）

### 图片 URL 要求

- 必须是可直接访问的图片 URL（`http://` 或 `https://` 开头）
- 海外优先：Google Places API 返回的 photo URL
- 国内优先：高德 POI API 返回的 photo URL → 百度重点补图 → 公开搜索结果
- 避免选择：水印过重的图片、尺寸过小的缩略图、需要登录才能查看的图片
- **严禁编造 URL**——如果搜索不到，留空即可

### 图片注入脚本模式（标准化）

搜图完成后，使用注入脚本将图片 URL 填入主脚本的 DATA section 中。

**注入原理**：
1. 读取 `photos.json`（中文名 → 图片 URL 列表的字典）
2. 逐行扫描主脚本，匹配以 `["` 开头、`],` 结尾的数据行
3. 用正则提取第 2 个字段（中文名），在字典中查找对应图片
4. 将行中第一个 `, "", "",` 模式替换为 `, "url1", "url2",`（即填充 img1/img2 字段）

**注入脚本模板**（参数化，复用时只需改 2 个路径）

变量：`PHOTOS_JSON`（搜图输出 JSON 路径）、`SCRIPT_PATH`（主脚本路径）

> **注入统计参考**：菲律宾 404 个 POI 搜图命中率 97%（393/404），注入 435 条数据行（大于 404 是因为部分 POI 同时出现在 ATTRACTIONS 和 DIVE_SITES 中，每条数据行独立注入）。

不同地图平台的地点导航 URI 格式不同。脚本 `scripts/gen_travel_scope.py` 内置三种平台的 URI 生成逻辑：

- 使用 WGS84 坐标系（原始经纬度）
- 全球通用

```
https://uri.amap.com/marker?position={lng},{lat}&name={name}
```
- 需要将 WGS84 坐标转换为 GCJ02 坐标系（中国大陆偏移）


- 坐标转换函数已内置在脚本中（`wgs84_to_bd09`）

>
> **[CRITICAL] 阈值历史**：原始阈值为 `lat < 0`，在印尼（纬度约-8°）未暴露问题，但菲律宾（纬度约10°N）被误判为国内导致地图路线功能失效。已修正为 `lat < 18`（中国大陆南界约18°N）。新建国家版本时务必确认此阈值覆盖目标国家纬度范围。详见「已知坑点与修复记录」章节。

## 完整 Pipeline 总览

从用户触发到最终交付，完整流程分为 10 个阶段。目的地发现、路线走廊探索和路线筛选是强制门槛，不能因为用户只提供了国家名、入境口岸或某个熟悉城市而跳过。每个阶段有明确的输入/输出文件和预估耗时（以多目的地国家攻略为基准）：

```
Stage 1: Intake SOP              → 参数确认（国家/自定义目的地/天数/预算/口岸/深度/地图平台/路线数）
Stage 2: 范围识别与目的地发现      → 建立全国或自定义范围的目的地候选池
Stage 3: 路线走廊探索              → 建立节点、交通边和成熟旅行走廊图
Stage 4: 候选覆盖与顺路性筛选      → 标记纳入、排除、排除原因和绕行成本
Stage 5: POI 数据收集             → 仅对正式纳入路线的目的地搜索酒店/餐厅/景点并交叉验证
Stage 6: 脚本构建                 → build_script 从 JSON 生成自包含 Python 脚本
Stage 7: 前置检查 + 批量搜图       → 代理/API 连通性测试 → 批量搜图
Stage 8: 图片注入                 → inject_photos 将图片 URL 注入脚本数据行
Stage 9: 生成交付与研究文件       → 输出交付版 Excel + 研究版 Excel + Markdown + HTML
Stage 10: QA 验证                 → 覆盖/走廊检查/图片计数/路线完整性/浏览器实测
```

### 超级深度模式的断点与临时存储 [CRITICAL]

**临时存储只允许保存中间证据，不能直接生成交付文件。** 所有交付生成必须通过正式运行 manifest，并完成目的地发现、路线探索、搜索引擎摘要取证、来源审计和预生成 QA。临时脚本调用 `gen_travel_scope.py` 时，如果没有 `TRAVEL_SCOPE_FORMAL_RUN=1` 及有效 manifest，生成器必须阻断。

国内搜索摘要证据还必须通过点位相关性检查：默认按 Google → 百度 → Bing 备用的顺序搜索，顺序由 `TRAVEL_SCOPE_SEARCH_ENGINES` 配置控制。百度这里指搜索引擎，不等同于百度地图地点检索配额。搜索结果摘要可作为百度地图缺失、评价数缺失和平台页面无法直接读取时的兜底，补充小红书/大众点评/携程的热度、特色和评价线索，但不得覆盖高德结构化评分、价格和坐标。结果摘要需命中点位名称或可识别名称片段，并且摘要或结果链接必须明确命中目标平台标识。仅因查询词包含平台名、或命中平台泛站首页的结果不得计入证据。Bing 可以作为备用源，但不得覆盖用户配置的主搜索引擎。

### 国内双地图结构化数据（强制）

国内点位必须先通过 `scripts/domestic_poi_sources.py` 完成高德主查询和百度交叉查询。两家来源字段必须并列保存，不得把一家的评分写入另一家的字段，也不得把高德 `poiweight` 当作评价数。百度没有匹配到具体点位时显示“百度未匹配”，不得用搜索摘要猜测补齐。

卡片和研究表展示：高德评分/评价数、有效搜索补充信息、AI推荐分。百度评分字段即使接口返回，也不作为国内主评分展示；百度图片仅在 API 返回具体字段时补充到缺图点位。所有国内点位生成高德导航和百度导航；导航坐标按平台要求转换，内部 WGS84 坐标不被覆盖。

卡片展示门禁：搜索补充字段全部为“待核验/待验证”时整块隐藏；高德评价数只有在拿到真实数值时才展示，缺失时只显示“高德评分：4.5”，不得在网页上展示“评价数：待核验”；研究台账仍可保留“接口未提供”状态。没有点位级证据的统一游玩时长不得写入卡片。

### 国内每日路线编排（强制）

每日行程不得按数组下标轮换或随机抽取点位。应调用 `scripts/domestic_itinerary.py` 或等价的正式路线编排器，在路线已确定的目的地走廊内，按点位质量、同日空间距离、已使用点位去重和住宿衔接选择 2-3 个景点→1 个餐厅→1 个住宿；同一路线内不得重复同一具体点位，通常每天形成 4-6 个点位。

开放时间、常规用餐时段、单日驾驶时长和雨天备选属于“参考提示”，用于避免明显不合理的安排，不得作为无数据时的硬性阻断条件，也不得要求旅行者严格照表执行。页面应明确标注“参考行程，实际以当天情况调整”；只有在出现明显冲突（例如闭馆时段或无法通行）时，才降低该点位的路线优先级并给出提示。路线编排不能退回到无约束轮换。

百度地图结构化查询需要环境变量 `TRAVEL_SCOPE_BAIDU_KEY`，并支持 `TRAVEL_SCOPE_BAIDU_MODE=core|deferred|skip`。`core` 只查询路线核心点，`deferred` 仅使用缓存并将未命中点位留待后续补齐，`skip` 完全不调用百度地图接口。缺失、配额超限、鉴权失败或接口错误时，正式国内生成必须停在配置/接口门禁，不得退化为假数据或旧的单一评分逻辑。运行报告必须记录百度匹配率，不能把“百度未匹配”计入百度评分覆盖率。搜索引擎仍可作为独立兜底，不消耗百度地图地点检索配额。

### AI 推荐分与平台评分隔离（强制）

每个正式点位都应生成独立的 `AI推荐分`，综合因子由配置控制，默认包括：主地图评分35%、评价量信号15%、POI/坐标/价格完整度15%、图片完整度10%、有效搜索热度与特色证据10%、路线与目的地适配度15%。缺少某项数据时使用明确的低置信度基准，不得伪造平台数据；该分数必须单独展示并标注“AI提供，仅供参考；非平台评分”。不得把 AI 推荐分写入高德、百度、携程、大众点评或小红书字段。

### 搜索性能与断点规则（强制）

搜索必须使用持久化缓存和运行目录断点文件；同一引擎、同一查询不得重复请求。搜索引擎按配置顺序执行，单点位达到最低有效相关证据数后停止继续搜索；使用有限并发和速率控制，禁止无界并发。超级深度必须分批保存结果，任何中断后从缓存和 checkpoint 续搜，不得重新扫描全部点位，也不得用临时脚本绕过来源审计。

超级深度或自定义大规模任务必须使用 `scripts/checkpoint_store.py`。不得把所有搜索结果长期保留在上下文或单个内存对象中。

运行结构：

```text
.temp/travel_scope_run_<timestamp>/
├── manifest.json
└── destinations/
    └── <目的地>/
        ├── hotels.jsonl
        ├── restaurants.jsonl
        ├── attractions.jsonl
        ├── evidence.jsonl
        └── dynamic_info.jsonl
```

强制规则：

- 初始化运行时生成唯一 `run_id`，manifest 保存国家、搜索深度、目的地状态和每类记录计数。
- 每完成一个点位或一条证据就追加写入对应 JSONL，并立即 flush + fsync。
- 每条记录必须有稳定 `record_id`；重试时按 `record_id` 去重，避免崩溃恢复造成重复记录。
- 每个目的地单独标记 `pending/running/completed/failed`，程序重启后只处理未完成项。
- 使用单写入者，搜索 worker 不得并行写同一个 JSONL 文件。
- 合并前必须读取并校验所有 JSONL；发现损坏行时直接报错，不得静默跳过。
- 只有合并后的研究数据完整，才能生成交付版和研究版文件。
- `.temp` 是可恢复中间层，研究版 Excel 是归档层，交付版文件不应被中途结果覆盖。

基本命令：

```bash
python scripts/checkpoint_store.py init --root .temp --country 印度尼西亚 --mode super_deep
python scripts/checkpoint_store.py status --run-dir .temp/<run_id>
python scripts/checkpoint_store.py append --run-dir .temp/<run_id> --destination 日惹 --category hotels --record-id hotel-yogya-001 --record-json '{"name":"..."}'
python scripts/checkpoint_store.py mark --run-dir .temp/<run_id> --destination 日惹 --status completed
python scripts/checkpoint_store.py merge --run-dir .temp/<run_id> --require-completed --output .temp/merged_research_data.json
```

不要把原始搜索结果全部重新注入模型上下文；应先保存原始证据，再向模型传递当前批次的结构化摘要和未完成清单。

### 关键约束

- **Stage 2 → Stage 3 [CRITICAL]**：必须先完成目的地候选池和范围筛选，再收集城市级 POI；不得因为口岸、熟悉度或搜索便利性直接缩小国家范围
- **Stage 3 走廊门槛 [CRITICAL]**：必须独立搜索成熟路线走廊，不能只按机场和城市名拼接；每个候选节点必须进入走廊、排除表或待验证表
- **超级深度 [CRITICAL]**：必须启用 `checkpoint_store.py`；每批数据落盘后才能继续下一批，崩溃后从 manifest 恢复，不得从头重搜
- **Stage 3 覆盖门槛 [CRITICAL]**：每个被发现的主要目的地必须标记为“纳入路线”“候选但排除”或“待验证”，不能静默遗漏
- **Stage 4 → Stage 5**：POI 数据必须持久化到 JSON 文件后才能构建脚本，不允许只在内存中传递
- **Stage 4 前置检查 [CRITICAL]**：搜图前必须先验证代理连通性（3 个 POI 测试，5 秒内返回结果算通过），否则会浪费大量时间排查超时
- **Stage 6 运行环境 [CRITICAL]**：海外目的地生成三件套时，Python 运行环境也必须设置代理环境变量（`HTTP_PROXY` / `HTTPS_PROXY`），否则 HTML 中的 Google Maps JS API 在浏览器中加载不受影响，但脚本日志可能误报
- **Stage 7 浏览器验证**：`file://` 协议在 Playwright 中被阻止，需启动 `python -m http.server` 本地服务器后通过 `http://localhost:port/` 访问

## 工作流程

### Step 1: 交互收集参数
通过 `question` 工具收集上述参数。如果用户消息已包含足够信息，可跳过部分或全部问题。

先识别用户的范围意图：

- **国家级输入**：如“印度尼西亚”“日本”“中国”，进入全国目的地发现流程。
- **单个或多个自定义目的地**：如“大理、丽江”“东京和京都”“巴厘岛、日惹”，只围绕用户指定范围规划；不得擅自扩展成全国攻略，但可以提示相邻目的地作为候选建议。
- **区域输入**：如“甘南”“新疆”“滇西北”，按区域内多个城市、景区和交通节点进行发现与组合。
- **线路输入**：如“青甘线”“川西环线”，按线路走向、入口、出口和沿线节点进行筛选；不能把线路名称当成单一城市。
- **口岸信息**：入境/离境机场、城市或港口只约束路线起点、终点和交通，不等于旅行范围。比如“巴厘岛入境、巴厘岛离境”不能自动变成“只规划巴厘岛”。
- **范围冲突**：用户同时提供国家和明确城市时，以明确城市范围为主，并说明国家级候选不会自动纳入。

### Step 2: 范围识别与目的地发现（强制阶段）
根据目的地范围判断数据源分流（国内 vs 海外）。国家级输入必须先盘点该国主要旅行目的地；自定义输入必须盘点用户指定的全部目的地，并可补充邻近候选，但不能用熟悉的单一城市替代目的地发现。

详细字段、候选池格式和搜索策略见 [references/destination-discovery.md](references/destination-discovery.md)。最低输出要求：

- 国家级输入：通常列出 8-16 个有代表性的城市、岛屿或自然目的地；小国或目的地较少时说明覆盖边界。
- 多目的地自定义输入：逐项列出用户指定目的地，并补充可能的顺路连接点。
- 国内目的地：支持用户自定义一个或多个城市/景区，不能强制套用“全国热门城市”模板。
- 每个候选必须记录区域、核心体验、建议停留天数、季节适配、交通枢纽、相邻目的地和数据可获得性。
- 候选池完成后才允许进入 Step 3；没有候选池不得直接搜索酒店、餐厅和景点。

通过在线搜索补充以下信息：
- 目的地名称（中英文）
- 所属区域
- 核心体验
- 建议天数
- 最佳季节
- 到达方式
- 主要交通连接、耗时、季节性中断风险
- 适合本次用户天数、预算和口岸约束的初步判断

### Step 3: 路线走廊探索（强制阶段）

在候选池完成后，先执行路线走廊探索，再决定哪些目的地进入 POI 深搜。使用 [references/route-exploration.md](references/route-exploration.md) 的节点—边模型，收集官方旅游资料、交通运营方、地图路线和成熟多日线路证据。通过以下命令执行确定性评分和覆盖门禁：

```powershell
python scripts/route_explorer.py --input <运行目录>/route_exploration_input.json --output <运行目录>/route_corridors.json
```

输入中如果存在 `subcorridors`，同样评分并输出；如果存在 `classic_corridors`，必须执行经典走廊覆盖审计。评分至少包含：走廊连续性25%、入口/出口适配20%、主题互补15%、天数适配15%、季节适配15%、绕行风险10%。输出必须包含每条走廊、子走廊和经典走廊审计结果、相邻节点交通边审计和未覆盖候选清单。没有走廊、必要子走廊或未处理的经典走廊输出不得直接进入 POI 深搜。

### Step 4: 候选覆盖与顺路性筛选
先对候选池进行范围覆盖检查，再设计路线。每个候选必须进入以下三类之一：

1. **正式纳入**：进入至少一条路线，并会继续收集城市级 POI。
2. **候选但排除**：保留在研究记录中，但不进入本次路线；必须写明排除原因。
3. **待验证**：关键信息不足，不能据此设计路线；必须写明需要补查的证据。

路线筛选必须考虑“顺路性”，至少评估：

- 是否形成合理环线或方向连续的线路
- 是否存在明显折返、跨区域跳跃或重复经过同一交通节点
- 城际交通耗时相对于总旅行天数是否过高
- 航班、船班、山路或季节性交通是否可靠
- 是否因加入某目的地导致其他核心目的地被压缩到不合理停留时间

不要为了满足“目的地数量”把明显绕路的地点硬塞进路线。可以把它保留为“候选但排除”，并解释“绕行成本过高”“交通不稳定”“季节不匹配”“停留时间不足”或其他可验证原因。

然后根据目的地地理位置和交通可行性，设计多条备选路线方案（通常3-6条）。每条方案包含：
- 方案名称、天数、路线串联、特色、适合人群、预算、交通方式
- 纳入目的地、排除目的地、主要折返点和交通风险

### Step 4.5: 每日行程编排（ITINERARY）

**为所有 ROUTES 中的路线方案编排完整的每日行程顺序。** 每个行程点位生成一条 ITINERARY 记录：

编排前先为每条路线建立 `route_plan.json`，至少声明路线节点顺序、主题和经典节点。不能先随机填满14天再给路线命名。

> **全量编排原则**：所有路线方案（方案A、B、C、D、E...）都必须编排完整每日行程，确保HTML下拉选择器中每条方案都有完整的地图路线展示和行程面板内容。不要只编排1-2条主路线，否则用户切换方案时看到的是空白页面，体验极差。

**ITINERARY 数据格式：**
```
# [方案名, 日序, 序号, 点位类型, 点位名称, 经纬度]
# 方案名: 对应 ROUTES 中的方案名称（必须完全一致）
# 日序: "Day 1", "Day 2", ... （字符串格式）
# 序号: 当日顺序（1, 2, 3, ...）
# 点位类型: 景点 / 餐厅 / 酒店 / 交通
# 点位名称: 必须与 HOTELS/RESTAURANTS/ATTRACTIONS 中的中文名完全一致（用于关联图片）
# 经纬度: WGS84格式 "纬度,经度"
```

**编排规则：**
- 每天约4-6个点位（含住宿、用餐、景点、交通节点）
- 点位名称必须与 HOTELS/RESTAURANTS/ATTRACTIONS 数组中的 `[1]中文名` 完全一致，脚本通过名称匹配自动关联图片URL
- 交通类型点位用于标注城市间移动（如"根河→漠河"），使用出发地坐标
- 经纬度直接从对应酒店/餐厅/景点的数据中复制，交通节点使用出发地坐标
- **所有路线方案都必须编排**，不可只编排部分方案
- 允许不同方案共享机场、港口和少量核心景点，但每条路线必须有不同的区域组合、节点顺序和每日结构；不能把同一日程复制后仅修改方案名称。

**编排实战经验：**
- 多方案可以共享少量交通枢纽或核心景点，但不能共享同一组主要点位；先编排方案A后，必须重新核对方案B/C/D/E的子线路、节点顺序、主题和交通风险。
- 每天的点位顺序应按实际游览路线排列（上午景点→午餐→下午景点→晚餐→酒店住宿）
- 跨城市移动用交通类型点位标注（如 Day3 最后一个点位是交通"额尔古纳→室韦"），次日从新城市开始
- 如果某方案新增了城市点位，必须先纳入统一数据模型、完成路线探索和QA，再编排行程。

**地图路线视图依赖此数据：**
- ITINERARY 为空时，HTML 地图 Tab 显示为禁用状态并提示"无行程数据"
- 地图引擎双轨制：国内目的地用高德JS API（需传 `--amap-js-key`），海外目的地用 Google Maps JS API（需传 `--google-maps-key`）
- 脚本通过 `_prepare_itinerary_json()` 函数将所有方案的 ITINERARY 数据注入HTML，下拉选择器自动填充所有方案名

### Step 5: 深度数据收集（含交叉验证）
只对 Step 3 标记为“正式纳入”的目的地，按数据源分流规则，通过在线搜索收集并交叉验证。候选但排除的目的地只保留必要的交通、季节和排除证据，不得为其完整搜索 POI 后再偷偷塞入路线。

**对每个点位执行以下流程：**
1. 搜索点位名称，收集至少对应搜索深度的交叉验证篇数（浅5篇/中10篇/深15篇/超级深23篇/自定义）
2. 交叉核对名称、地址、评分、价格
3. 确认点位真实存在且正常营业
4. 获取精确坐标（国内→高德POI搜索；海外→Google Maps）
5. 搜索并提取2张可用图片URL（详见"图片搜索与填充流程"章节）

**数据量标准：**
- **住宿**：按用户选择的搜索深度（浅5家/中8家/深10家/超级深15家/自定义），使用**真实酒店名称**，不能用区域名
- **餐厅**：按浅3家/中6家/深8家/超级深12家/自定义执行，使用真实餐厅名
- **景点**：按浅3个/中6个/深8个/超级深12个/自定义执行，使用真实景点名

### 证据台账（必须保留）

每个点位至少保留一条结构化证据记录，并在达到交叉验证篇数时保留完整来源清单：

```text
点位ID
来源URL
来源类型：官方 / 地图平台 / 攻略 / 点评 / 新闻 / 交通运营方
核验日期
来源支持的事实：存在 / 地址 / 营业 / 评分 / 价格 / 图片 / 坐标
是否独立来源
冲突或疑问
状态：已确认 / 待复核 / 已排除
```

不能用搜索结果摘要数量代替证据台账，也不能把同一文章在多个转载站点的副本算作多个独立来源。

**每条数据需包含的字段（11字段格式）：**

| 数据类型 | 字段顺序（索引0-10） |
|---|---|
| HOTELS（住宿） | 旧字段 `[0]-[10]` 保持不变；追加高德POI ID、 高德评分/评价数、百度UID/匹配名称/地址/坐标/评分/评价数/价格/图片/匹配状态、AI推荐分 |
| RESTAURANTS（美食） | 旧字段 `[0]-[10]` 保持不变；追加同上双地图结构化字段和 AI推荐分 |
| ATTRACTIONS（景点） | 旧字段 `[0]-[10]` 保持不变；追加同上双地图结构化字段和 AI推荐分 |
| DIVE_SITES（潜水） | `[0]目的地, [1]中文名, [2]英文名, [3]类型, [4]价格(元), [5]评分, [6]经纬度, [7]图片URL1, [8]图片URL2, [9]适合等级, [10]描述]` |

> **注意**：ATTRACTIONS 的评分([5])后直接跟经纬度([6])，再跟图片([7][8])，最后是游玩时间([9])和描述([10])。与其他数据类型的字段顺序略有不同。

### Step 5: 城际交通信息收集（必做）
> **[CRITICAL] 交通信息是必做步骤，不可跳过。** 多目的地攻略中，城际交通直接影响路线可行性和预算估算，缺少交通信息的攻略不完整。

对路线中每两个相邻目的地之间，搜索并收集以下交通信息。交通数据分为两层：

- `TRANSPORT_NODES`：可独立定位的真实节点，例如“墨宝汽车站”“墨宝港口”，每个节点必须有自己的名称、坐标和来源/核验状态。一个目的地可以有多个交通节点。
- `TRANSPORT`：点到点交通路线边，记录方式、公司、票价、耗时、班次、距离、预约要求和注意事项。

当一个目的地有多个节点时，`TRANSPORT` 可在扩展字段中填写“出发节点/到达节点”，精确链接到 `TRANSPORT_NODES`；不应只写目的地名，否则路线可能无法判断应使用汽车站还是港口。

HTML只展示 `TRANSPORT_NODES`，地图路线也按节点分别落点；Excel同时展示节点明细和完整路线边。旧版只有路线边时允许兼容生成，但端点必须标记为“待补充具体车站/港口”，不得把目的地名称冒充已核验站点。

**搜索关键词策略：**
- 海外：`"城市A to 城市B" transport` / `"城市A 城市B" ferry schedule` / `"城市A 城市B" bus fare` / `12go.asia 城市A 城市B`
- 国内：`"城市A到城市B" 交通` / `"城市A 城市B" 大巴 时刻表` / `"城市A 城市B" 火车 票价`

**每条交通数据需包含的字段（兼容旧9字段，推荐扩展为12字段）：**

| 字段 | 示例 |
|------|------|
| 路线 | 宿务→薄荷岛 |
| 交通方式 | 快船（OceanJet） |
| 运营公司 | OceanJet |
| 参考票价(元) | 80 |
| 行程时间 | 2小时 |
| 班次频率 | 每日06:00/09:30/13:00 |
| 出发地坐标 | 10.2941,123.8799 |
| 目的地坐标 | 9.6456,123.8533 |
| 备注 | 购票建议提前1天；码头税25比索另付；行李限重15kg |
| 距离 | 约120公里 |
| 是否需预约 | 建议提前预约 |
| 来源/核验状态 | 官方船期页；出发前复核 |

**注意事项：**
- 同一段路如有多种交通方式（如飞机+船），全部列出
- 票价统一换算为人民币
- 班次频率尽量给出具体发车/起飞时间，而非"每日多班"
- 备注列写购票建议、行李限制、额外费用、淡旺季班次变化等实用提示
- 搜索2-3篇来源交叉验证票价和班次信息

### Step 6: 实用信息与动态字段
根据目标国家收集：签证政策、汇率、现金建议、SIM卡、通讯、电压、时差、语言、最佳季节、旺季提醒、安全提示、紧急联系、旅行保险、防晒/防寒、环保、小费、交通提示等

## HTML 结构规范

HTML 地图标记页采用**双视图Tab切换**设计，包含两个Tab页：

### Tab 1: 卡片列表视图

按以下层级组织：

```
目的地城市（一级分类，可展开/收起）
├── 住宿（二级分类）
│   ├── 酒店A
│   │   ├── 图片1 + 图片2（缩略图，点击可放大）
│   │   └── [地图平台] 导航按钮
│   └── 酒店B
│       ├── 图片1 + 图片2
│       └── [地图平台] 导航按钮
├── 美食（二级分类）
│   └── ...
├── 景点（二级分类）
│   └── ...
├── 潜水/特色活动（二级分类）
│   └── ...
└── 交通（二级分类）
    └── ...
```

**禁止**按"住宿→目的地"或"美食→目的地"的大类优先结构。必须以目的地城市为一级分类。

## 脚本使用说明

`scripts/gen_travel_scope.py` 是一个通用模板脚本，包含：
1. **坐标转换区**（COORIDNATE TRANSFORMATION）：WGS84↔GCJ02↔BD09 转换函数
2. **地图URI生成区**（MAP URI GENERATORS）：按地区生成可用导航链接
3. **数据区**（DATA section）：所有数据以 Python 列表内联定义
4. **Excel 生成区**：支持11个工作表的交付版和14个工作表的研究版，均带格式化（表头蓝底白字、边框、自动列宽、冻结首行）；研究版包含目的地覆盖、来源证据和动态信息台账
5. **HTML 生成区**：双视图Tab设计——①卡片列表视图（按目的地→子分类组织，多地图平台按钮，每个点位含2张图片展示+lightbox）②地图路线视图（双引擎：国内用高德JS API / 海外用Google Maps JS API；Marker按类型着色+序号标签，连线按天着色/同天实线/跨天虚线，InfoWindow含图片+导航按钮，左侧行程面板flyTo定位，路线选择器切换方案）
6. **Markdown 生成区**：完整文字攻略，含每日行程详情章节
7. **Checkpoint 存储区**：`checkpoint_store.py` 提供运行初始化、增量追加、状态标记、断点读取和研究数据合并

### LLM 使用流程

1. 在 Step 2-6.5 收集完所有数据（含交叉验证、覆盖表、证据台账、动态信息和 ITINERARY 每日行程）
2. 将 `gen_travel_scope.py` 复制到工作目录 `.temp/` 文件夹
3. 编辑脚本 DATA section 的各数据数组，填入真实数据（含 ITINERARY 数组）
4. 首次运行脚本生成交付版三件套和研究版 Excel（图片URL可暂留空，地图Key可暂不传）
5. 按城市批次搜索图片URL，通过批量填充脚本模式补全图片
6. 重新运行脚本生成含图片的最终版本（国内目的地传入 `--amap-js-key` 启用高德地图路线视图；海外目的地传入 `--google-maps-key` 启用Google Maps路线视图）
7. 将交付版三件套和研究版 Excel 一并移动到用户指定的输出目录；研究版不在公开营销或普通用户交付中默认展示

## 数据质量要求

1. **真实名称**：酒店/餐厅/景点必须使用真实存在的名称，不能编造
2. **准确坐标**：
   - 国内：经纬度基于高德地图POI搜索获取，格式 `"纬度,经度"`（WGS84格式存储）
   - 海外：经纬度基于 Google Maps 实际位置，格式 `"纬度,经度"`
3. **交叉验证**：每个点位必须经过至少 `交叉验证篇数` 篇内容的交叉验证，确认真实存在
4. **评分来源**：国内以高德结构化评分为主，百度只重点核验；海外以Google平台为主；AI推荐分独立计算并标注为非平台评分
5. **旺季价格**：价格以出行月份的旺季参考价计算（人民币）
6. **预算范围**：住宿主体价格在用户选定预算范围内，允许少量超预算高端和经济型
7. **数据达标**：每个目的地的酒店/餐厅/景点数量必须达到用户选择的搜索深度标准
8. **图片可用**：每个点位2张图片URL，必须从真实网页搜索提取，不能编造URL。找不到的留空，HTML自动显示📷占位图
9. **目的地覆盖完整**：国家级输入必须有候选池和覆盖表；自定义多目的地输入必须逐项处理；任何主要候选都不能静默消失
10. **路线顺路性可解释**：正式路线应说明主要方向、折返点和交通代价；明显绕路目的地必须列入排除表并给出原因

## 常见问题与注意事项

### Q: 国内目的地应该选择哪个地图平台？
A: 国内推荐选择"高德地图"或"全部"。高德URI标记接口（uri.amap.com/marker）支持点击后直接收藏到高德地图收藏夹，非常实用。

### Q: 图片URL搜索不到怎么办？
A: 按优先级尝试：① 高德POI图片 ② 百度重点补图 ③ 公开搜索结果 ④ 留空并显示缺图状态。不要编造URL或复用其他点位图片。

### Q: 小型经济酒店/民宿搜不到坐标怎么办？
A: 按优先级：① 搜索该酒店所在街道/商圈的坐标 ② 搜索该酒店所在城镇的中心坐标 ③ 在数据中标注"坐标待确认"并告知用户。

### Q: 数据量太大，搜索轮次太多怎么办？
A: 采用分批策略——先完成所有目的地的基础信息（名称、坐标、评分、价格），生成第一版三件套。然后按城市分批搜索图片URL，通过批量填充脚本模式逐步补全。通常3-4轮即可完成150+点位的图片填充。

### Q: 脚本运行报错怎么办？
A: ① 检查 `pip install openpyxl` 是否已安装 ② 检查数据数组中每行字段数量是否一致 ③ 检查是否有引号/逗号语法错误 ④ 用 `python -c "exec(open('脚本路径').read())"` 快速检测语法

### Q: 多条路线方案的每日行程都要编排吗？
A: **是的，所有路线方案都必须编排完整每日行程。** 如果只编排1-2条主路线，HTML下拉选择器切换到其他方案时会显示"该路线暂无详细行程编排"，用户体验极差。实战中多方案通常有大量重叠点位，编排效率很高——先编排方案A，再基于A的骨架调整出其他方案即可。5条方案约200-250条ITINERARY记录，编排工作量约1-2小时。

### Q: 编排行程时发现某方案涉及新城市，但数据数组中没有该城市的点位怎么办？
A: 先把新城市纳入目的地覆盖表和统一POI数据模型，再重新执行路线探索、来源审计、图片补充和QA，最后由正式生成器输出。坐标统一使用WGS84格式。

## 已知坑点与修复记录

以下为实战中踩过的坑及修复方案，新建国家版本时务必逐条检查：

### 坑点1: `_is_overseas()` 坐标阈值错误

**现象**：菲律宾（纬度约10°N）被误判为国内目的地，导致地图路线功能失效（坐标转换函数误将海外坐标当GCJ02做偏移，Marker位置严重偏移）。

**根因**：原始阈值为 `lat < 0`，仅考虑了南半球。印尼（纬度约-8°）未暴露问题，到菲律宾才触发。

**修复**：阈值的判定条件改为 `lat < 18`（中国大陆南界约18°N），完整条件为 `lat > 55 or lat < 18 or lng < 70 or lng > 140`。

**检查清单**：新建国家版本时，确认目标国家纬度范围。东南亚国家（菲律宾10-19°N、泰国5-20°N、越南8-23°N）在边界附近时尤其注意。

### 坑点2: Day 字符串排序错误

**现象**：HTML地图路线视图中，行程面板的Day列表和地图图例中，Day10 排在 Day2 前面，导致地图路线从 Day1 直接跳到 Day10。

**根因**：JavaScript 默认字符串排序，`"Day10" < "Day2"` 为 true（按字符逐位比较）。

**修复**：排序前用 `parseInt(day.replace('Day ', ''))` 提取数字，按数字大小排序。

**代码位置**：`renderRoute()` 函数中的 Day 排序逻辑，以及图例生成逻辑。

### 坑点3: 日志输出与实际地图引擎不一致

**现象**：海外目的地运行脚本时，控制台日志打印 "AMap JS API loaded"，但实际 HTML 中使用的是 Google Maps JS API。

**根因**：脚本中日志输出语句硬编码了 "AMap JS API"，未根据 `overseas` 变量动态切换。

**修复**：将硬编码的日志改为根据 `overseas` 变量动态输出：
```python
if overseas:
    print(f"[INFO] Google Maps JS API enabled for overseas destination")
else:
    print(f"[INFO] AMap JS API enabled, key: {amap_js_key[:8]}...")
```

**教训**：脚本的日志输出必须与实际逻辑分支一致，避免误导排查方向。

### 坑点4: 代理前置检查缺失

**现象**：菲律宾攻略搜图时，Clash Verge service 进程在运行但代理核心（verge-mihomo）未启动，混合端口 7897 无人监听。直接运行搜图脚本导致全部超时（10分钟只处理2个POI），浪费大量时间排查代理配置。

**根因**：搜图前未做代理连通性前置检查，盲目信任 "service 进程在跑 = 代理可用"。

**修复**：搜图前必须执行三级检查（详见「图片搜索与填充流程」章节的前置条件检查）。

**教训**：Clash Verge 的 `clash-verge-service` 进程存在不代表代理核心已启动，必须验证端口实际监听。Python 的 `urllib.request` 不会自动走系统代理，必须显式设置 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量。

### 坑点5: Google Places API classic 版已废弃

**现象**：调用 classic 版 Places API（`/maps/api/place/nearbysearch/json`）返回 `REQUEST_DENIED` 错误，状态码为已废弃。

**根因**：Google 已将 classic Places API 标记为 deprecated，新项目无法使用。

**修复**：改用 Places API (New)（`/v1/places:searchText` 和 `/v1/places:searchNearby`），请求头设置 `X-Goog-Api-Key` 和 `X-Goog-FieldMask`。

**验证方法**：在 Google Cloud Console 中确认 Places API (New) 已启用，classic 版 API 可在控制台看到 deprecation 标记。

### 坑点6: `file://` 协议在 Playwright 中被阻止

**现象**：用 Playwright 打开 `file:///D:/.../xxx.html` 验证地图路线时，JavaScript 无法正常执行，地图不渲染。

**根因**：Playwright 安全策略阻止 `file://` 协议加载外部 JS 资源（如 Google Maps JS API）。

**修复**：在 HTML 文件所在目录启动 `python -m http.server 8899`，通过 `http://localhost:8899/xxx.html` 访问。

## 跨平台适配说明

本技能的脚本 `gen_travel_scope.py` 是纯Python + openpyxl，任何能跑Python的环境都能直接使用。但SKILL.md中描述的工作流依赖特定工具能力，在其他Agent平台上使用时需注意：

### 各平台适配对照

| 能力 | 技能运行环境 | 本地脚本 | 通用LLM |
|------|----------------|----------|----------|
| 联网搜索 | 宿主AI或用户提供 | 不在脚本中硬编码供应商 | 手动或平台工具 |
| 交互问答 | 按Q0-Q9标准化收集 | 读取统一数据模型 | 手动对话 |
| 图片搜索 | 按国内/海外数据源分流 | 处理URL与缺图状态 | 平台工具 |
| 运行脚本 | 执行正式生成器和QA | Python + openpyxl | 用户本地 |
| 坐标转换 | 统一WGS84存储 | 脚本内置 | 脚本内置 |

### Codex 适配要点

Codex具备联网搜索和代码执行能力，核心工作流可以迁移：

1. **数据收集**：用Codex的Web搜索替代 `online_search`，搜索逻辑和关键词策略完全一致
2. **交叉验证**：同样执行多源搜索+交叉核对，搜索策略不变
3. **坐标获取**：国内调用高德POI REST API为主，百度只验证重点点位；海外使用Google Maps/Places
4. **图片获取**：国内高德图片优先、百度补图、公开搜索兜底；海外按Google/公开搜索补充
5. **脚本生成**：将数据填入 `gen_travel_scope.py`，在Codex沙箱中直接运行生成三件套
6. **交互参数收集**：用Codex的函数调用替代 `question` 工具

### 移植步骤（Codex/Astra等）

1. 将SKILL.md作为System Prompt的核心指令喂给Agent
2. 将 `gen_travel_scope.py` 放入Agent可访问的工作目录
3. 将 `references/destinations.md` 作为参考文档提供
4. Agent按SKILL.md的Step 1-8流程执行，用平台原生搜索工具替代 `online_search`
5. 高德POI API Key通过环境变量或参数传入
6. 最终生成三件套文件交付用户

> **关键提醒**：脚本本身是跨平台的，不需要修改。需要适配的只是数据收集和搜索这层——由宿主Agent提供搜索能力，并按国内/海外数据源规则注入统一数据模型。脚本生成、坐标转换、Excel/HTML/Markdown渲染全部在脚本内部完成。
